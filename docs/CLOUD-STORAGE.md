# Direct cloud storage feasibility

Study only; no direct cloud connector is implemented. Checked against the providers' official documentation on November 14, 2026. A direct connector would enumerate and stream original audio through the provider API without requiring its desktop sync client. Each connection would remain a separate Macarok source.

## Provider comparison

| Provider | Direct access and seeking | Indexing, authentication, and writes |
| --- | --- | --- |
| Dropbox | Feasible. Content downloads support a single HTTP byte range and `206` responses, suitable for seeking in original audio. | Stable file IDs and revision tokens; folder cursors provide incremental changes. Desktop OAuth supports PKCE and refresh tokens. Existing music outside an app folder requires Full Dropbox content access, with the narrowest read scopes possible. Writes need separate permission and revision conflict checks. [Download behavior](https://docs.dropboxapi.com/dropbox-api/docs/technical-reference/request-response-formats), [changes](https://docs.dropboxapi.com/dropbox-api/docs/detecting-changes), [OAuth](https://docs.dropboxapi.com/dropbox-api/docs/oauth). |
| Google Drive | Feasible for uploaded binary audio: `files.get` with `alt=media` supports byte ranges. Google Workspace export is a different operation. | Persist file IDs and parent relationships; use the changes feed after enumeration. Broad existing-library access uses restricted scopes; `drive.file` covers files explicitly shared with the app rather than arbitrary account-wide access. Review the consent and verification requirements before committing. [Downloads](https://developers.google.com/workspace/drive/api/guides/manage-downloads), [changes](https://developers.google.com/workspace/drive/api/guides/manage-changes), [scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth). |
| S3-compatible storage | Feasible. S3 `GetObject` supports byte ranges; sign requests or obtain short-lived signed URLs. Compatibility must be tested for each server. | Bucket/object keys form the hierarchy; store version/ETag information. Tag editing requires uploading a changed object, not editing audio tags through object metadata. Credentials and URL expiry vary by deployment. [GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html), [PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html), [signed URL lifetime](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html). |
| WebDAV, including Nextcloud | Feasible with `PROPFIND` for folders and `GET` for bytes. Probe range support: WebDAV availability alone does not establish usable seeking on every server. | Paths, ETags, size, and modification times support an index. Nextcloud supports app-password authentication. `PUT` can replace writable files; conditional updates must be supported and verified. [Nextcloud file operations](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/WebDAV/basic.html), [HTTP range semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-14). |
| iCloud Drive | Prefer a user-selected folder through the native filesystem and File Provider route. Files may need downloading before access. | Coordinate filesystem reads/writes and perform blocking materialization off the main thread. CloudKit exposes app containers; it should not be treated as a generic REST browser for all of a user's iCloud Drive. This integration recommendation follows Apple's documented storage models. [Coordinated file access](https://developer.apple.com/documentation/foundation/improving-performance-and-stability-when-accessing-the-file-system), [CloudKit containers](https://developer.apple.com/documentation/cloudkit/ckcontainer). |

## Shared design requirements

- **Authentication:** native OAuth connectors should use the system browser, authorization code flow, PKCE, and refresh tokens where supported. Keep credentials in Keychain. Persist provider IDs, never expiring signed URLs, as track identity. Refresh authorization before opening or seeking; retry an expired credential once, then expose a reconnect action. [Google native application flow](https://developers.google.com/identity/protocols/oauth2/native-app), [native OAuth guidance](https://www.rfc-editor.org/rfc/rfc8252).
- **Playback:** original bytes and Macarok's existing buffer policy. A playback resolver must supply fresh authorization for every new request. Validate `206` and `Content-Range`; a server returning the whole file cannot be treated as a successful partial response. A bounded local file cache is the fallback for formats or servers requiring more data. Authenticated HTTP access and VLC seeking need an integration spike before selecting a transport implementation.
- **Indexing:** provider listings contain filesystem metadata, not a complete music library. Download enough audio to read tags, with per-format limits and a full-file fallback; do not assume every tag or embedded cover is at the beginning. Cache extracted metadata and images by provider ID plus revision, use incremental changes where available, and bound concurrency and cache size.
- **CUE and artwork:** retrieve CUE and cover sidecars from the same remote parent as their audio; resolve CUE paths within the selected source. Keep virtual track boundaries in SQLite and stream the shared original file. Shared drives, case rules, and access restrictions require provider-specific resolution.
- **Tag writes:** start read-only. A later explicit write flow downloads a complete original, applies TagLib changes locally, verifies it, and uploads the replacement with conflict detection. A changed remote revision must trigger review rather than overwrite. Distinguish writable audio, writable CUE sidecars, and local-only edits; a CUE plus audio update is not assumed atomic.

## Recommended sequence

Start with a **read-only Dropbox connector**: documented range downloads, stable IDs, incremental cursors, and native PKCE offer a clear first implementation to validate. This is an engineering recommendation, not a measured prototype result. Follow with WebDAV for self-hosted libraries, then S3-compatible storage and Google Drive after their deployment and consent requirements are settled. Handle iCloud Drive through a dedicated native file-source path.

Keep cloud file access behind source capabilities such as enumeration, range reads, change tracking, artwork retrieval, and optional conditional writes. Spotify, Qobuz, Deezer, and Bandcamp remain separate future integrations and unavailable in this iteration; this study does not establish playback API access for any of them.
